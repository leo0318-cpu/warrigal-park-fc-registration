# 4.1 Member CRUD — design notes (work package WBS 4.1)

Owner: Zhou Kunpeng · Branch: `feature/member-crud` · Status: design drafted, not yet implemented

This note records the design decisions behind the member register before any code is
written. It exists so that the Configuration Management Report (Assignment 2, Part B)
describes a branching model that was actually used, rather than one invented after the fact.

## Scope of this work package

From the WBS: *Member CRUD, persistence, search by name (including players who share a name)*.

| Entity | Fields | Notes |
| --- | --- | --- |
| Member | member_id, given_name, family_name, date_of_birth, contact details | `member_id` is generated by the system, never supplied by the user |
| Guardian | guardian_id, name, contact details | Separate entity — one guardian may link to many members (WBS 4.2) |
| Registration | registration_id, member_id, season, status | Owned by WBS 4.3, referenced here only for search ordering |

## Decisions taken

1. **Search must not collapse people who share a name.**
   The 2024 incident (a player took the field unregistered) traces back to records being
   confused when two players share a name. Search therefore returns *all* matches and
   requires the registrar to disambiguate by date of birth, never by name alone. This is
   acceptance criterion 2 of US-01.

2. **Members are deactivated, never deleted.**
   Registration history must survive for insurance and audit purposes (Decision Log D-06).
   `deactivate` sets a flag; the record remains queryable.

3. **Every required field is validated before persistence.**
   A missing required field rejects the whole record and names *every* missing field in one
   error message, rather than failing one field at a time.

4. **Persistence is deliberately boring.**
   The charter fixes the budget at $0 (Constraint 3.3) and the deliverable as a Python
   command-line application. SQLite via the standard library therefore satisfies both the
   economic and technical constraints with no third-party dependency to procure — this is
   the reason the Procurement Plan (Part A) contains no database licensing line item.

## Branch discipline applied to this package

- Work happens only on `feature/member-crud`, never directly on `main`.
- `main` accepts a merge only when the work package meets the Definition of Done: unit tests
  pass, the acceptance criteria of the linked story are demonstrably met, and the README
  reflects the change.
- The branch is merged through a pull request reviewed by another team member; the reviewer
  must not be the author.
